# docu-ai

Compiles a folder of Markdown files into a single, properly formatted Google Doc: real Docs styling, code
blocks, tables, and one tab per chapter. **Zero markdown residue in the output** — no `**`, no backticks, no
`|` table pipes. The output should be indistinguishable from a document a careful human formatted by hand.

`plan.md` holds the locked decisions and milestone sequence. **This file holds the engineering rules.** When the
two disagree, this file wins and `plan.md` should be corrected.

## Commands

    npm test                          # unit + golden snapshots. MUST pass with no Google credentials present.
    npm run test:live                 # tier 3: real API, real readback, real residue lint. Needs DOCU_AI_LIVE_TESTS=1
                                       # (the npm script sets it) and a cached token from `npm run auth`.
    npm run build                     # tsc
    npm run lint                      # ESLint — code-quality gate, typescript-eslint recommendedTypeChecked
    npm run auth                      # one-time browser consent; caches a refresh token
    npm run probe                     # verify assumptions against the live API (see below)
    npm run m0                        # build the M0 proof document
    npm start -- preview <dir>        # parse + plan a folder, print its structure — no network, no quota spent
    npm start -- build <dir> [title]  # build a doc: one tab per chapter, plus a cover with a clickable TOC
    npm start -- lint <documentId>    # re-run the residue lint against an already-built document
    npm start -- layout <documentId> [maxPages]   # page count + page-break warnings for a built document
    npm start -- trash <documentId>   # move a document docu-ai built to Drive's Trash (restorable for 30 days)
    npm start -- letter <dir> [out]   # a cover letter in the letter look (resume <dir> for a CV): one file, no cover; writes out.pdf AND out.docx, prints the page count
    npm start -- export <documentId> [out.pdf|out.docx]   # export a built document; the extension picks the format (no extension: PDF)
    # build, resume and letter also take  --title "..."  and  --replaces <documentId>  (see "Word, PDF and replacing" below)
    npm run mcp                       # serve preview/build/layout/lint/info/trash/list/export/save_export over MCP on stdio

Don't confuse the two "lint"s: `npm run lint` is ESLint checking source code quality; `npm start -- lint` is the
CLI subcommand that reads a *built Google Doc* back and re-runs the markdown-residue lint against it.

One-time Google Cloud setup is in SETUP.md.

If `npm test` ever requires credentials to run, that is a bug. Nobody runs tests that need auth.

## Mental model — read this before touching `emit/`

**A Google Doc is not a tree. It is a flat buffer of UTF-16 code units with styling laid over index ranges.**

Every piece of pain in this codebase follows from that one fact. There is no "insert a styled paragraph"
operation — you insert characters, then you style the range those characters landed in. Insert anything earlier
in the buffer and every index after it shifts. Internalise this and the architecture below is obvious; fight it
and you will spend days on off-by-one bugs.

## Architecture — layers and hard boundaries

    md files → [1] parse  → mdast                   knows markdown, knows nothing about Google
             → [2] plan   → DocPlan IR              semantic, not visual
             → [3] emit   → Request[]               pure; the only layer that knows the Docs API
             → [4] verify → readback + lint         reads only

The boundaries are the design. Violating one is the main way this project rots:

- **`parse/` must never mention Google.** It produces mdast and nothing else.
- **`plan/` must never mention fonts, colours, sizes, or indices.** DocPlan is semantic: `{kind: 'code', lang:
  'python'}`, never `{font: 'Roboto Mono', size: 10}`. If you find yourself putting a visual property in the IR,
  it belongs in `theme/`.
- **`theme/` is the single home of every font, colour, size, and spacing value.** A hardcoded font name or hex
  literal anywhere else in `src/` is a bug, not a shortcut.
- **`emit/*` must be pure functions.** No network, no clock, no randomness — snapshots must be byte-stable
  across runs. The sole exception is `emit/document.ts`, the orchestrator, which is the *only* module in the
  codebase permitted to do I/O.
- **`verify/` never mutates.** It reads the built doc back and asserts. Repair requests, when we add them, get
  generated by `emit/` like everything else.

## Two front doors, one implementation

`src/operations.ts` holds what docu-ai can be asked to do, as data in and data out: `preview`,
`buildDocument`, `lintDocument`, `layoutDocument`, `documentInfo`, `trashDocument`. The CLI (`cli.ts`) formats those results for a person; the MCP
server (`mcp/server.ts`) returns them as JSON to a model. **Neither door wraps the other.** A door
that delegates to the other inherits its output format, its exit codes and its assumptions about who
is reading, and the two drift the moment either is changed for its own audience. Nothing in
`operations.ts` writes to stdout or sets an exit code — that is a front door's job.

`preview` is the one operation that takes no `AuthProvider`, and that is deliberate: it is the
approval surface, annotated `readOnlyHint` over MCP so a caller can tell at a glance which tool is
safe to run unattended.

**Credentials come in; they are never discovered.** `GoogleOAuthProvider` takes a `GoogleAuthConfig`.
`authConfigFromEnvironment()` is the single place the environment is read, and
`GoogleOAuthProvider.fromEnvironment()` is the named escape hatch that front doors call — library
code never does. As long as a tool reaches into the environment for its own credentials, "where
identity lives" is a fact every tool must agree on, and the second tool either duplicates the lookup
or imports the first to borrow it. That second option is precisely the cross-module auth import that
made personal-ai's supposedly independent modules non-independent.

**`zod` is a direct dependency, pinned to the range the MCP SDK itself resolves, so npm dedupes to
ONE copy.** This is the `google-auth-library` trap again in a new place: two copies of a schema
library yield two nominally distinct types and `registerTool` rejects a schema built with the wrong
one. `npm ls zod` must show a single deduped entry; check it before bumping either package.

`plan/` is deliberately a seam. The LLM planner (chapter segmentation, tab titles and emoji, code-language
detection, table captions) lands *there* and nowhere else. Deterministic v1 must not close that door.

**Never put a model in `emit/`.** Index arithmetic is unforgiving and non-negotiable; a model will drift on a
40-page document and the failure will be silent.

## The index discipline

The four-phase write sequence exists to make indices knowable. Do not deviate from it:

1. Create doc → `addDocumentTab` per chapter → `updateNamedStyle` × N **per tab** → `updateDocumentStyle` for
   margins. Theme goes in *first* so inserted content inherits correctly instead of needing a restyle pass.
2. Per tab, insert **all plain text** in document order with a running cursor, with `insertTable` placeholders
   where tables go. Insert lengths are exactly known here, so a running cursor is legitimate.
3. `documents.get(includeTabsContent: true)`. This readback is the index source of truth *and* the verification
   oracle.
4. Emit all styling against the indices from step 3.

Rules that follow:

- **Indices are UTF-16 code units, which is exactly what JS `String.length` returns.** Use `.length`. Do *not*
  use `[...s].length` or count code points — that is correct-looking and wrong for emoji and any astral char.
- **Never carry a cursor from step 2 across into step 4.** Re-derive from the readback. A cursor is valid only
  within the single insert pass that produced it.
- **Any request that changes document length** must either be in the final pass applied in **descending index
  order**, or be followed by a fresh readback. Table cell fills and bullets both change length.
- **The body's first insertable index is 1, not 0.** Index 0 is not a valid location.
- **The document always ends in a newline you cannot delete.** To append, use `endOfSegmentLocation`, not a
  computed tail index.
- **Never hand-compute table cell indices.** Read them back and fill cells in reverse order. And when
  you do: a cell's insertion point is its first paragraph's `startIndex`, never the cell's own
  `startIndex` — a cell wraps a paragraph, it isn't one, and Docs rejects an insert at the cell bound
  with a 400 ("must be inside the bounds of an existing paragraph").
- **`createParagraphBullets` consumes the leading tabs that express nesting**, so it shortens the text. Bullets
  are applied *last*, after every other styling request.

## Style and inheritance rules

- **A paragraph inherits its style from the paragraph before it.** A code block will bleed monospace and grey
  shading into the next body paragraph. Set every block's paragraph style explicitly; never rely on inheritance
  across a block boundary.
- **Always enumerate `fields` masks explicitly. Never send `fields: '*'`** unless you positively intend to reset
  every unspecified property to its default. Explicit masks also keep snapshot diffs readable.
- **Paragraph borders cannot be partially updated.** Setting `borderLeft` means supplying the complete
  `ParagraphBorder` — `color`, `width`, `padding`, `dashStyle`.
- **`updateNamedStyle` is per-tab.** Applying the theme to tab 1 does nothing for tab 2.
- **Fonts silently fall back when Docs doesn't know them, and a readback cannot see it.** The reference
  for `WeightedFontFamily.fontFamily` says an unrecognised font renders as Arial — and that substitution
  happens at *render* time, so the API stores and returns whatever name we sent. `documents.get` will
  report success while every reader sees Arial. **Only PDF export + `pdffonts` can prove a font applied**,
  which is what `npm run probe` does. Themes may only use fonts from `VERIFIED_FONTS` in `theme/fonts.ts`;
  `assertVerifiedFonts()` enforces it before any build, and a font is added to that list only on the
  evidence of a probe report — never because it ought to be there.
- **`ParagraphStyle.indentStart` is a no-op in Docs' PDF export — verified live, not assumed.** Set via
  a per-paragraph override or baked into a named style, at 24pt or 200pt, with or without a border on
  the same paragraph: `documents.get` echoes the value back correctly every time (proven via `bodies()`
  readback), and the exported PDF's glyph positions (`pdftotext -bbox`) never move — five separate test
  documents, 2026-08-19. `indentEnd` has no such problem; it's what narrows the prose column in every
  named style already. **A stored value is not proof of a rendered one — this is the same lesson as the
  font fallback, generalised past fonts.** Never reach for `indentStart` for a left inset; use border
  `width`/`padding` instead (see `emit/blocks.ts`'s `quoteStyleRequest`, which scales both by nesting
  depth for exactly this reason).

## Verified API facts — and a warning about Google's docs

Verified against the live discovery document on 2026-08-19:

- `addDocumentTab`, `deleteTab`, `updateDocumentTabProperties` **exist**. Tabs take `title`, `iconEmoji`,
  `index`, `parentTabId` (nested sub-tabs are possible). Every request carries `Location.tabId`.
- `updateNamedStyle` **exists** → redefine `TITLE` / `HEADING_1..6` / `NORMAL_TEXT` per tab.
- `ParagraphStyle` has `shading`, `borderLeft/Right/Top/Bottom`, `keepWithNext`, `keepLinesTogether`,
  `avoidWidowAndOrphan` → real code blocks and blockquotes with no 1×1-table hacks.
- `pinTableHeaderRows` exists → table headers repeat across page breaks.
- `Link.headingId` / `Link.tabId` exist → clickable hand-built TOC and cross-tab links.
- **No** `insertTableOfContents` → the TOC is hand-built. **No** page-number auto-field → footers are static text.

**Live-verified by `npm run probe` on 2026-08-19**, in a run whose controls both behaved:

- `addDocumentTab` genuinely works. **A new document already has one tab, titled "Tab 1"** — so
  whichever tab is meant to come first (the cover, in the current design) must *rename that tab* with
  `updateDocumentTabProperties`, not add a tab. Adding one leaves a stray empty "Tab 1" ahead of it.
- `\v` really is an in-paragraph line break: it survives readback inside a single text run rather than
  splitting the paragraph. Use it for markdown hard breaks.
- Both `snake_case` and `camelCase` field masks are accepted. We use snake_case, matching the reference.
- 24 fonts embed correctly, including every monospace candidate (Roboto Mono, IBM Plex Mono, JetBrains
  Mono, Source Code Pro, Fira Mono, Space Mono, Inconsolata). `VERIFIED_FONTS` holds the confirmed list.

**Live-verified building M3 (tables) on 2026-08-20:**

- **A fresh document body opens with an implicit `sectionBreak` before any content.** Invisible in a
  small hand-inspected probe — neither `.paragraph` nor `.table` matches it, so a naive "if paragraph
  ... else if table" walk silently skips it and never reveals it's there — but it throws off any
  lockstep count-based reconstruction by exactly one at real-document scale. `compileStyleRequests`
  filters `body.content` to `.paragraph`/`.table` elements before walking it, rather than assuming the
  first element is always real content.
- **A table cell's own `startIndex` is not a valid insertion point.** `insertText` at a raw
  `cell.startIndex` fails: "the insertion index must be inside the bounds of an existing paragraph." A
  cell wraps a paragraph, it isn't one — insert at `cell.content[0].startIndex` (one past the cell's
  own bound) instead. See `emit/table.ts`'s `extractCellParagraphRanges`.
- **`endOfSegmentLocation` chains correctly** across mixed `insertText`/`insertTable` requests within
  one `batchUpdate`, applied in array order — confirmed live, which is what lets every block in a
  build be appended in document order with no cursor arithmetic needed to position any of them.
- `updateTableCellStyle`'s `tableStartLocation` and `tableRange` are **mutually exclusive** ("oneof
  field 'cells' is already set") — pass only `tableRange` (it carries its own start location nested
  inside `tableCellLocation`) when targeting a specific range, never both.
- `updateTableColumnProperties` needs an explicit `fields` mask like every other update request —
  omitting it isn't a silent no-op, it's a 400.
- `TableCellStyle.contentAlignment` is **vertical** (`TOP`/`MIDDLE`/`BOTTOM`), not the horizontal
  left/center/right markdown's `:---:`/`:---`/`---:` columns need. Horizontal alignment is a
  **paragraph** property — apply `ParagraphStyle.alignment` to the cell's own paragraph instead.
- Header shading, borders, and column widths all **render as stored** — unlike `indentStart`, PDF
  export confirms these live, and `pinTableHeaderRows` genuinely repeats the header across a real
  multi-page table (verified on a 15-row table split across 3 pages).

**Live-verified building M4 (tabs, cover, TOC) on 2026-08-20:**

- **`documents.create`'s own response already includes the initial tab's id** (`data.tabs[0].tabProperties.tabId`) — no readback needed just to learn it. And **`batchUpdate`'s `replies[]` maps 1:1 to the request array**, so `addDocumentTab`'s reply carries the new tab's id directly. Tab creation for an entire document — rename the initial tab, add every other chapter's tab — is one batch with zero readbacks, regardless of chapter count.
- **`EndOfSegmentLocation` and `Location` both take a `tabId`**, and mixed `insertText`/`insertTable`/`addDocumentTab` requests **chain correctly across tabs within one `batchUpdate`**, applied in array order. No cursor arithmetic is needed to position anything in any tab — everything is appended in document order.
- **A paragraph's `headingId` is not assigned until that paragraph has actually been styled with a `HEADING_*` namedStyleType** — it does not exist at the readback that follows the initial plain-text insert. Linking to a chapter's heading from elsewhere (a table of contents) needs a **second** readback, taken after the styling pass that applies `HEADING_1` has already landed. Two readbacks total, not one per chapter.
- **Cross-tab heading links need `Link.heading = {id, tabId}`, not the legacy bare `Link.headingId`** — confirmed live: the legacy field's own docs say it's only unambiguous "in documents containing a single tab." `Link.heading` (like `Link.url`) auto-applies Docs' default link colour + underline; nothing extra to set.
- **PDF export of a multi-tab document auto-inserts a title page for each tab**, showing its tab title in Docs' own default heading style — before that tab's actual first page. This is a PDF-export artifact, not something a reader sees in the Docs UI itself; don't mistake these extra pages for real body content when reviewing a multi-tab build's PDF, and don't assume the same page count maps 1:1 onto the web-view scrolling experience.

**Live-verified building the full 9-chapter real corpus (~417KB source, 1301 paragraphs) on 2026-08-20:**

- **`addDocumentTab` rejects a tab title over 50 characters with a 400** ("The tab title cannot be
  longer than 50 characters"), invisible at every earlier test scale because no fixture chapter title
  ran that long — a real chapter H1 did. Fixed in `emit/document.ts`'s `tabTitle()`: truncated at a
  word boundary with a trailing ellipsis, applied only to the tab-strip label. The cover's TOC keeps
  the chapter's full, untruncated title as its link text — the two are no longer the same string past
  this point, on purpose.
- **`Link.url` does not validate that the value is a real URL — it silently coerces a bare relative
  string by prepending `http://`.** An inline markdown link between sibling chapter files (e.g.
  `[01-api-layer.md](01-api-layer.md)`, a real pattern in this corpus's own overview table) round-trips
  as `http://01-api-layer.md`: a syntactically valid but non-resolving URL. This is a genuine fidelity
  gap, not a crash — nothing catches it at build time or in the residue lint, since the link text
  itself contains no markdown syntax. **Fixed** (2026-08-20): `plan/fromAst.ts`'s `planDocument` now
  resolves any link whose href matches a sibling chapter's own source filename into a `chapterLink`
  Inline node, which `emit/` turns into a real `Link.heading` — the same mechanism the cover TOC
  already used. See "Cross-chapter link resolution" below for the one non-obvious part of building it.
- The residue lint correctly flagged exactly one real finding in the full corpus, and it was a genuine
  source defect, not a converter bug: an unmatched triple-backtick (` ```json `) sitting mid-sentence in
  `07-shared-infrastructure.md` with no closing fence. CommonMark has no valid pairing for it, so it
  parses as literal text — verified by hand against the raw mdast output — and a correct converter has
  no more business "fixing" that than a human transcriber would invent a closing fence the source never
  had. Confirms the lint's code-font exemption is working as designed, too: the same corpus legitimately
  contains 18 literal `|` characters and 14 `**` sequences (Python `**kwargs`, `int | None`-style type
  unions, enum-like `"a"|"b"` strings) inside real inline-code runs, and none of them false-positived.

**Cross-chapter link resolution (2026-08-20)**, and the one thing about it that isn't obvious: a
table cell's own chapter-crossing link resolves at a genuinely different TIME than an ordinary
paragraph's, not just different code.

- A paragraph's text already exists by the time phase 3's readback happens, so a link found there has
  a stable range — it's safe to resolve to `Link.heading` as late as phase 7, well after headingIds
  are known, the same way the cover's TOC entries always have.
- A table cell's text does **not** exist until phase 6 (`tableCellFills`) inserts it, and per
  `tableCellFills`'s own long-standing rule, a cell's fill and its own styling can never be split into
  separate requests — anything length-changing landing between them invalidates one half. That rule,
  which already governed a cell's bold/code/URL styling, turned out to apply just as much to a cell's
  chapter link: **first attempt at this feature deferred cell links to the same late phase as
  paragraphs, and it silently failed live** — the range captured during the cell-fill phase had gone
  stale by the time the deferred request tried to use it, because other cells/bullets filled between
  them shifted it. Caught by the live integration test, not by any unit test, because the bug only
  exists at the *timing* between two live API round trips — no snapshot test replays that.
- The fix was reordering when the second readback happens: it now lands **between** the
  non-length-changing style pass (phase 3, which is what applies `HEADING_1` and is what makes
  headingIds discoverable at all) and the length-changing pass (phase 6, table fills + bullets),
  rather than after both. That means `tableCellFills` can resolve a cell's chapter link to
  `Link.heading` immediately, inside its own atomic fill unit — see `emit/compile.ts`'s
  `compileChapterContentRequests` / `compileChapterLengthChangingRequests` split and
  `emit/document.ts`'s phase comments for the full sequencing.

**Syntax highlighting (2026-08-20, M7).** Per-run `updateTextStyle.foregroundColor` — untested by any
prior milestone, since only `namedStyles.ts` had ever set foreground colour, at named-style level —
**does render**, PDF-verified before any implementation was written (this file's own culture: a stored
value is not proof of a rendered one, and this project has been burned by exactly that inference once
already with `indentStart`). Tokenizer is `lowlight` (highlight.js), not Shiki: Shiki loads grammars
asynchronously, which would force `planChapter` async and ripple through `cli.ts` and every test;
lowlight is sync and emits ~20 stable, documented class names rather than baked colours, so `theme/`
keeps owning the palette instead of importing one. Two things worth recording:

- **`documents.get` appends a paragraph's trailing `\n` to its LAST text run's `content` string, not
  to a run of its own.** A code paragraph's final token (e.g. `1` in `return x + 1`) reads back as
  `"1\n"`, not `"1"`. Not new behaviour, exactly — `test/live.build.test.ts`'s table-cell assertions
  already `.trim()` around it — but this is the first time it bit an *exact-equality* check outside a
  table cell, so it's worth naming explicitly: any readback assertion comparing a text run's content
  by exact string equality must account for this, not just table cells.
- **A block-wide `updateTextStyle` and per-run token colours must never both touch
  `foreground_color` on overlapping ranges** — `codeBlockStyleRequests`'s own text request is issued
  *after* the per-run requests in `compile.ts`, so leaving `foreground_color` in its mask for a
  tokenized block silently overwrites every token's colour with the block's base one. Every request
  succeeds; only a PDF render or a readback that actually inspects `foregroundColor` (not just "was a
  request sent") reveals it. Fixed by dropping `foreground_color` from that one request's mask when
  the block is tokenized (`highlighted: true`), not by reordering — see `codeBlockStyleRequests`'s own
  doc comment, including the one deliberate cosmetic gap this leaves (unclassified characters inside a
  highlighted block render in Docs' own default colour rather than the theme's exact base grey —
  visually indistinguishable at reading size, left as-is on purpose).

Palette (`theme/presets/technical.ts`'s `codeBlock.syntax`) is deliberately small — 7 entries, grounded
in what the real 9-chapter corpus's 11 highlightable fences actually produce (175 tokens, 9 distinct
highlight.js classes measured), not a guess at highlight.js's full vocabulary. An unrecognised class
falls back to the block's base colour, never throws, never invents one.

**Images (2026-08-21, M8).** `insertInlineImage` only ever accepts a `uri` — confirmed against the
discovery doc, not assumed — which Google fetches once, at insert time. No bytes field, no Drive-file
reference. Constraints from the same doc: under 50MB, under 25 megapixels, PNG/JPEG/GIF only (no
WebP, no SVG), and the `uri` itself under 2kB.

- **A file uploaded to the user's own Drive cannot be used as that `uri`, even made fully public —
  live-verified, not a guess.** Tried all four commonly-documented forms (`webContentLink`,
  `drive.google.com/uc?export=view`, `...?export=download`, `lh3.googleusercontent.com/d/{id}`)
  against the same probe document, before AND after granting "anyone with the link" reader access,
  and again after an 8-second propagation delay. **All four failed every time.** A genuinely external
  URL succeeded immediately on the identical document and request shape, isolating the failure to
  Drive-hosted URLs specifically. Consequence: a local markdown image (`./diagram.png`, the common
  real pattern) has no v1 embedding path; only a markdown image that already names a public http(s)
  URL embeds. Don't re-attempt a Drive-URL workaround without genuinely new evidence — this was tried
  thoroughly, not casually.
- **`insertInlineImage` does not create its own paragraph — verified live.** Inserted bare via
  `endOfSegmentLocation`, it merges straight into whatever paragraph currently sits at the end of the
  tab (confirmed: text → image → text in one batch produced ONE paragraph containing both the image
  and the following text, not three). A leading and trailing `'\n'`, each its own `insertText` request
  flanking the `insertInlineImage` one, is what gives it a clean paragraph of its own — the leading
  `'\n'` terminates whatever paragraph preceded it rather than opening a new element of its own, so
  the image's own structural element in a later readback is exactly one paragraph, not three.
- **A "2x"/retina filename is not proof of an image's real pixel dimensions — trust the fetched
  bytes, never the URL.** The live test's own fixture (Google's logo, filename
  `googlelogo_color_272x92dp.png`) is a genuine retina asset: its actual PNG header reports 544×184,
  exactly double the filename's claim. Reading real IHDR/GIF-header/JPEG-SOF bytes (already the
  design, on principle) caught this automatically — trusting the filename would have inserted the
  image at 112pt past this theme's 432pt column.
- **Nothing before this milestone had ever needed the page's absolute width.** Margins are relative
  offsets and `indentEnd` narrows relative to them; code blocks reset to "full width" without ever
  computing a number. Capping an image to "the theme's usable column" is the first thing that needed
  an actual page width in points — so `theme/types.ts`'s `PageSpec` now carries explicit
  `widthPt`/`heightPt` (612×792, matching what this theme's margin comments already assumed), and
  `documentStyleRequest` sends `pageSize` explicitly rather than leaving it to whatever the account's
  own locale default happens to be (Letter in a US-locale account, A4 elsewhere).
- **`image-size` (the obvious dependency) was installed, then deliberately removed.** `npm audit`
  surfaced two unfixed high-severity DoS advisories — infinite loops in its ICNS/JXL/HEIF parsers,
  formats this project will never touch since Docs only embeds PNG/JPEG/GIF. `emit/image.ts` instead
  hand-parses exactly those three formats (PNG/GIF: fixed-offset header reads; JPEG: a bounded marker
  walk, hard-capped at `MAX_JPEG_MARKERS` iterations so malformed input fails fast instead of hanging).

**A résumé build (2026-09-09) surfaced two more facts, one about tabs and one about `\v`, both live-verified
with a control on the same document rather than assumed:**

- **Renaming a document's own sole native tab — via `updateDocumentTabProperties`, for ANY reason, even
  back to its own default name — is what makes Docs' PDF export prepend a blank interstitial title page.**
  Not a multi-tab-only effect as the M4 note above first characterised it: isolated with a control on one
  single-tab document — inserted a paragraph and exported (1 page), then renamed that same tab and
  exported again with no other change (2 pages, the new first page reading just the tab's title). Renaming
  it *back* to the default `"Tab 1"` still produced the extra page — neither the tab count nor the title's
  value is what matters, only whether the rename call was ever made. Consequence for `emit/document.ts`'s
  `createTabs`: a build with exactly one tab and no cover must send **zero** tab-property requests and
  leave the native tab exactly as `documents.create` made it — the cost is a tab strip that reads "Tab 1"
  nobody will ever navigate; the benefit is a résumé PDF that opens on the résumé, not a blank page reading
  the candidate's own name. Once a second tab exists this protection is moot anyway (Docs emits a title
  page per tab regardless, per the existing M4 note), so the special case is narrow on purpose: sole tab,
  no cover, nothing else.
- **A bare `\v` in-paragraph hard break — on its own, no bullets, no punctuation, nothing else unusual —
  is enough to make Docs' PDF export embed Times New Roman**, alongside whatever font the theme actually
  asked for. Isolated with the smallest possible live reproduction: one NORMAL_TEXT paragraph set to
  Source Serif Pro, containing nothing but `'line one text\vline two text\n'`, exported with `pdffonts`
  showing both `SourceSerifPro-Regular` and `TimesNewRomanPSMT`. The Times glyph is never visible — it's
  an invisible zero-width control character the break itself carries (confirmed present in `pdftotext`'s
  raw extraction, confirmed absent from the rendered page image at reading resolution) — so this is NOT a
  VERIFIED_FONTS violation and does not need a workaround: every visible character in a build still renders
  in a theme font exactly as `assertVerifiedFonts` requires. Recorded because it's the same category of
  fact as the bullet glyph's own Arial embedding (M0's font-fallback note generalised: an invisible
  structural glyph can silently pull in a font the theme never named, and only a PDF font list — never a
  readback — can show it). Don't mistake a `pdffonts` report that includes Arial or Times New Roman for a
  fallback bug on its own: check whether the glyph is actually visible before treating it as one.

Schema presence is not proof an endpoint behaves, and a stored value is not proof of a rendered one.
`npm run probe` is the standing answer to both: it exercises `addDocumentTab`, checks whether `\v`
really is an in-paragraph line break, confirms the field-mask dialect, and PDF-verifies every font
candidate. **Read its CONTROLS block first** — it applies Arial (must embed) and a fake font (must fall
back), and if those two misbehave the rest of the report proves nothing.

> **Google's published "Work with tabs" guide is stale.** It reads as though tab creation is UI-only. It is not.
> Do not delete working tab code because a prose doc page contradicts it. **The discovery document is the only
> authority**, and it is one command away:
>
>     curl -s 'https://docs.googleapis.com/$discovery/rest?version=v1' | jq '.schemas.Request.properties | keys'

## API request conventions

- Type every request as `docs_v1.Schema$Request`. No `any`, no untyped object literals — the compiler checking
  request shapes is the main reason this project is in TypeScript.
- All dimensions in points, via a `pt(n)` helper. Never a bare `{magnitude, unit}` literal.
- Colours live in `theme/` as hex and pass through one converter to `OptionalColor`. Never hand-write
  `{rgbColor: {red: 0.2, ...}}` inline — 0–1 floats are easy to get subtly wrong and impossible to review.
- **`batchUpdate` is atomic**: one invalid request and nothing in that batch applies. Good news for consistency,
  but it means chunking a large build into several batches gives up atomicity — so a failed build must be
  restartable by wipe-and-rebuild, never left half-written.
- **The per-user write quota is tight.** Batch aggressively: one `batchUpdate` carrying 300 requests, never 300
  calls. Never call `documents.get` inside a loop. If you think you need a round trip per element, re-read the
  four-phase sequence. (Check the current quota figure before tuning chunk sizes.)

## Dependencies — two traps, both already sprung

- **`googleapis` must be >= 176.** The npm package's generated types lag the live API by a long way:
  144.0.0 has no `addDocumentTab` and no `updateNamedStyle` at all, so the two requests this design
  leans on hardest do not typecheck. If a request exists in the discovery document but not in
  `docs_v1.Schema$Request`, the package is too old — upgrade before doubting the discovery doc.
- **Never add `google-auth-library` as a direct dependency.** googleapis pins an exact version and
  nests its own copy; a second copy at the root yields two nominally distinct `OAuth2Client` types
  (they differ by a private field) and `google.docs({auth})` rejects the client you built. Take the
  type from googleapis instead: `import type { Auth } from 'googleapis'` → `Auth.OAuth2Client`.

## Testing

Three tiers, and the first two are where the real work happens:

1. **Golden request snapshots.** Fixture `.md` → emitted `Request[]` JSON. No network. The snapshot diff *is*
   the code review for any change to `emit/`. An unexplained snapshot change is a bug until proven otherwise.
2. **IR assertions.** Fixture `.md` → DocPlan, asserted structurally. Catches parse and planning errors without
   involving the API at all.
3. **Live integration**, gated behind an env var (`npm run test:live` → `test/live.build.test.ts`). Builds a
   real tabbed doc against the real API, asserts structure via readback (tab titles, table cells, cross-tab
   TOC links resolving to the right `headingId`), and runs the residue lint. Requires a cached token
   (`npm run auth`) and trashes the doc it creates when done — it is not part of `npm test` and never runs in
   an environment without credentials.

**Every gotcha that bites once becomes a fixture**, named for the bug it prevents (`nested-list-tab-eating.md`,
`code-block-style-bleed.md`). This is how the gotcha list above stays true instead of becoming folklore. M1's
two live-only bugs are on record this way as inline test cases rather than separate fixture files — see
`test/fromAst.test.ts`'s multi-line-code-span test and `test/blocks.test.ts`'s ordered/unordered-transition test,
both with a comment naming the real corpus content that triggered them.

The residue lint is the headline requirement expressed as a test: read the built doc back and assert no literal
`**`, backtick, or `|`-pair survives in prose, and no line starts with an unconverted `#`/list marker. It is
**not** "these characters never appear" — a code-styled run (mono font from the `code` mark) is exempt, because
real code legitimately contains all of them (Python `**kwargs`, shell pipes, a Python `#` comment). The anchored
start-of-line checks apply to a paragraph's full text, never to an individual inline-styled run, since a run
boundary falls wherever styling changes — often mid-sentence — and checking every run's start against a
start-of-line pattern flags ordinary prose that happens to follow a styled span with a literal `+` or `-`.

## Layout: what only the PDF can say (2026-10-15)

A built document's page count, and where its page breaks fall, are decided when Docs lays the page out;
the readback has neither. So `build` exports the PDF (the same export `probe` uses for fonts), reads each
page's text with `pdftotext` and reports `layout: {pages, lastPageLines, warnings}` — `verify/layout.ts`,
whose analysis is a pure function of the pages' text and the document's paragraphs, tested with no network.
Three warnings: a heading (or a heading with its lead line) that ends a page whose content starts on the
next; more pages than `maxPages`; a last page of a few lines. The reasons it is built the way it is:

- **`keepWithNext` on a heading is not enough, and the stored value proved nothing** (the `indentStart`
  lesson again). `heading3` kept a role's heading with its dates line; the pair still fell at the foot of
  page 1 with the bullets on page 2, on two real CVs in one day. The fix is a *lead line* rule in the
  theme, `keepLeadWithNext: [2, 3]` (résumé only): a paragraph directly under such a heading keeps with the
  block after it, **unless that block is a heading of the same or a higher rank** — then the lead is the
  whole entry (an education line, a summary paragraph) and there is nothing to strand it from. The same
  rule is in `compileBlocks` (what gets marked) and `keepGroups` in `verify/layout.ts` (what counts as
  stranded); the first live run flagged an Education entry before the detector learned it, so keep the two
  in step. `technical` sets nothing and its snapshots did not change.
- **Verified live on a control**: the same CV with filler pushing the project heading to the foot, built
  with `keepLeadWithNext` off and on. Off: page 1 ends with the heading and its stack line, bullets on page 2
  (flagged). On: page 1 ends on a bullet, and the heading, line and first bullet start page 2 together.
- **The match is on whole lines, from a line boundary.** A bullet that merely ends in a heading's last word
  must not read as that heading. `pdftotext` keeps zero-width spaces and bullet glyphs; `squash()` strips
  the spaces, and the glyph lines never match a heading.
- **A document of several tabs is not measured** (`measured: false`, with the reason): Docs' PDF export adds
  a title page per tab (M4), so its page count is not what a reader scrolls through. A missing `pdftotext`, or
  a failed export, is also `measured: false` — never an exception, and never "no warnings": `layout` is always
  present, so an empty `warnings` can only mean the pages were looked at and were fine. The backend image
  carries `poppler-utils` for this.
- **`trash`, with `info` as its approval preview.** Every rebuild makes a new Doc, so superseding one needs a
  way to clear the old. `trash` sets Drive's `trashed` flag (restorable for 30 days; not a delete), refuses
  anything that is not a Google Doc, and — because the scope is `drive.file` — can touch only documents
  docu-ai built. Its MCP `_meta` names `info` (read-only) as the tool the assistant's gate shows instead of a
  bare id: "Google Doc “X” · created … · last edited … · link".
- **A 403 on a full Drive now says so.** `documents.create` answered "The caller does not have permission" for
  every build while the account sat at 15.00 of 15 GB. `explainFailure` (drive.ts) reads the storage quota on
  a 403 and, only when usage has reached the limit, replaces the message with the real cause (keeping Google's
  words in it). A 403 with room left stays a 403. Unit-tested against the shape Google sent; not run live,
  since the storage is no longer full.

## The letter look (2026-10-15)

A real cover letter built in the résumé look came out cramped and top-heavy: 10pt type, 4pt between paragraphs, a 22pt
name over a page 60% empty. A CV is scanned and packed; a letter is read and needs room. `theme/presets/letter.ts` is
10.5pt Source Serif at 115% with 10pt between blocks, inch side margins and 60pt top and bottom, and a 17pt name. Chosen
by measuring, not by taste: the same 330-word letter spilled its two-line closing onto page 2 at 11pt (even with the
margins trimmed) and sits on one page with room to spare at 10.5pt; looked at in the exported PDF. Same full-width
rule as the résumé (`indentEndPt: 0`), same fonts, no `keepLeadWithNext` (a letter has no roles). `build` refuses
several files for a letter as it does for a résumé. Two things the look cannot give a letter, both in the markdown:
a **date line** (the model does not know today's date) and **room to sign** (markdown has no gap; a hard-break
closing is as close as it gets).

## Word, PDF and replacing a document (2026-10-29)

Closes gap-plan step 1 (`../plan.md`, "Gaps found on 2026-10-24"), which the user approved on 2026-10-29.

- **A Word export asks Drive for an array buffer**, as the PDF export always did (`exportDocumentWith`). `../plan.md`
  (2026-10-24) records it coming back as a `Blob`, read as a string, which threw; that has not been reproduced
  here (see the last point). A `Blob` is read if a client sends one. **Every export
  is checked for what it is**: a PDF must open with `%PDF-`, a `.docx` with `PK` (it is a zip). Garbage from Drive,
  such as a sign-in page, is an error naming the document, never a file handed on as a CV.
- **`export` takes its format from the name** (`formatForPath`): `.docx` Word, `.pdf` PDF, no extension PDF (what it
  always did). Any other extension is refused before Drive is asked anything, because a `.txt` that holds a PDF is
  worse than an error.
- **`resume` and `letter` write both files and print the layout report.** `out.pdf` and `out.docx` (`outputPair`:
  `cv`, `cv.pdf` and `cv.docx` all mean that pair), because a CV goes out as whichever one the employer asks for.
  They now print the page count and any page-break warning, as `build` did; before, only `build` did, and a comment
  above `reportLayout` that described the residue lint made it read as though `resume` did too (the comment is
  moved to `reportResidue`). A name given with no extension used to be written as a PDF with exactly that name; it
  is now `name.pdf` and `name.docx`.
- **`--title` names the document in Drive.** A CV and a cover letter from one person are both titled with their
  first heading, the sender's name, and sit in Drive as two documents with the same name. The MCP `build` already
  took a `title` (its description wrongly said it applied to the cover only); the CLI's `resume` and `letter` now
  take `--title`, and `build` accepts it as well as its old second argument. Giving both is an error.
- **`--replaces <id>` moves the old document to the Trash, after the new one is finished.** Three rules, each tested
  with the Google calls stubbed and their order recorded (`test/replaces.test.ts`), and each shown to be caught by
  breaking the code on purpose:
  1. **The old document is checked before anything is built** (`checkReplaceable`): not a document docu-ai built, or
     already in the Trash, and nothing is spent.
  2. **Only a clean build replaces anything.** Leftover markdown or a layout warning means the new document is not
     finished, and the old one is the last good one: it is kept, and the result says why. (The CLI already treats both
     as exit code 1, so "clean" is the same as "exits 0". A layout that could not be measured is not a problem found.)
  3. **A failed trash never loses the new document.** `replaceSuperseded` does not throw; the result carries
     `replaced.trashed: false` and the reason.
- **`replaces` is not on the MCP door, on purpose.** Through a model it would trash a document inside the approval of a
  build, which would show an opaque id. The existing `trash` tool avoids exactly that: its approval is previewed by
  `info`, which names the Doc. The model keeps trashing a superseded Doc with `trash` after a build, as `build`'s
  description says. Add it to the door only together with a preview of what it would trash.
- **Not run against Drive yet (2026-10-29):** all of the above is unit-tested with Drive stubbed. The Google login had
  lapsed (`invalid_grant`), so a real Word export, a real `resume` with both files and the page count, and a real
  `--replaces` have not been seen. Record them here when they have. **A real Word export has now been seen**
  (2026-10-30, through `save_export`): two real documents, 654,050 and 651,163 bytes, each opening with `PK`. A real
  `resume` with both files and a real `--replaces` still have not.

## Saving an export for another tool: `save_export` (2026-10-30)

A file cannot travel through a model: one reply holds 16,000 tokens, and a Word CV is at least 217,000 as base64 (a
cover-letter PDF, the smallest real file, at least 17,000). So a CV reaches an email by path. `save_export` exports a
document and writes it into `DOCU_AI_EXPORTS` (injected by `tools.yaml`: the assistant's `uploads/exports`, which
mail-ai is given as the one folder it may attach from) and returns `{path, filename, size}`, never the bytes
(`src/exports.ts`). The rules, each tested; the name, overwrite and no-folder rules were also each shown to be caught by
breaking the code in a copy:

- **A tool of its own, not a flag on `export`.** `export` is read-only and the web app's download button uses it;
  a tool that writes a file is not read-only, so chat asks before `save_export` runs, and its approval shows `info`
  (the document's title and link) as `trash`'s does. `export`'s description now says never to use it to attach.
- **The name is the recipient's**, chosen by the model, so it is checked like an upload's: no slash, control
  character or reversing mark, no leading dot, at most 120 characters, and it ends in the format's extension (a
  `.pdf` name for a Word file is refused, not given a second extension).
- **Nothing is overwritten.** `name.docx`, then `name (2).docx`, written with the exclusive flag so there is no
  check-then-write race; the returned name says which.
- **No folder, no save**, before Drive is asked anything. The folder is created on first use.
- The escapes for the reversing marks are written as `\u202a`…, never as the characters themselves: a first
  version held the invisible characters in the source, and only a scan for them found it.

## Definition of done for a feature

Fixture added → IR asserted → request snapshot reviewed → live doc built → readback assertions pass → residue
lint passes → opened in Docs and looked at once with human eyes. The last step is not optional: this project's
requirement is *presentation*, and no assertion catches a code block split across a page break.

## Don'ts

- Don't use Drive's `text/markdown` import as the engine. It can't build tabs, you can't control its output, and
  anything it fails to parse stays in the document as literal markdown — the one thing we promise never happens.
- Don't reach for a workaround before checking the discovery doc for a native request. The 1×1-table code-block
  hack, widely recommended online, is unnecessary — paragraph `shading` exists.
- Don't add an inline `documents.get` "just to be safe". Fix the phase ordering instead.
- Don't let `plan.md` milestones justify breaking a layer boundary. Shipping order is negotiable; the boundaries
  are not.
